# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| maintainer-alive | In eval mode, the Repo facts block's `last 5 default-branch commits` (dates and authors) and `maintainer first-response sample`; also the issue Comments with `author_association`. In live mode, inspect the default-branch commit history and the dates of Owner/Member/Collaborator replies in recently updated issues and this issue. | At least **one** human-authored default-branch commit (or a bot merge of a human PR) occurred in the last **180 days**, **or** an Owner/Member/Collaborator replied to an issue within the last **90 days**. Bot-only commits that do not merge human work do not count. | required |
| repo-in-use | In eval mode, the Repo facts block's `archived`, `latest release`, and `last push to any branch` fields. In live mode, check the repository's archive banner, Releases box, and recent branch activity. | The repository is **not archived**, and either its latest release was published within the last **365 days** or a branch was pushed within the last **180 days**. A repository that has never published a release can still pass through the recent-push condition. | required |
| actionable-contribution | The issue title, body, and Comments in the eval bundle; the same issue title, body, and thread in live mode. | The issue requests a change to code, tests, documentation, or behavior, or reports a defect that could be fixed. **Fail** if it is solely a question about how to use the existing project, with no requested or reported change. | required |
| bounded-scope | The issue title, body, and Comments, including any maintainer clarification about the expected change (in the eval bundle or the live issue thread). | The requested work is **one identifiable fix or enhancement**, or a maintainer-defined checklist for **one feature/component**. **Fail** if it is expressly a tracking/umbrella issue intended to be split into separate contributions, requires a broad rewrite or changes to core internals according to a maintainer, or leaves the design unresolved after discussion. A short issue body, missing reproduction steps, or a multi-item acceptance checklist for one change does **not** fail by itself. | required |
| issue-unclaimed | In eval mode, the Repo facts fields `this issue: assignees:` and `linked PRs:`, plus PR mentions and dated claim/progress comments in Comments. In live mode, inspect the issue's Assignees and Development boxes and its complete comment thread. | **No current assignee**, **no open PR** implementing this issue (linked formally or mentioned in the thread), and **no explicit claim or work-in-progress update within the last 30 days** by another contributor. A request for permission alone without a statement of work is not a claim; a claim older than 30 days with no newer progress is stale and does not block. Closed, unmerged PRs are not *active* claims; consider them under `attempt-history`. **In Path Review live mode only**, apply `scope.md`: other students' claim comments do not block the issue, but assignees and open PRs still count. | required |
| ai-contribution-allowed | In eval mode, the Repo facts `contribution policy` field and any policy text quoted in the bundle. In live mode, check `CONTRIBUTING.md`, any linked contributor guidance, dedicated AI-policy files, and PR templates. | **Pass** if there is no stated AI-use restriction, or if AI-assisted contributions are allowed subject to requirements such as disclosure, author understanding, tests, or human review. **Fail** if the repository explicitly bans the AI-assisted/generated contributions this course requires. A conditional policy is not a ban. | required |
| maintainer-response | In eval mode, the Repo facts `maintainer first-response sample` and dated Owner/Member/Collaborator replies in Comments. In live mode, inspect the same kinds of responses in recently updated issues and this thread. | At least **one** sampled issue received its first Owner/Member/Collaborator reply within **30 days** of opening. | preferred |
| release-recency | In eval mode, `latest release` under Repo facts; in live mode, the repository Releases box. | The latest published release is dated within the last **365 days**. No releases or an older release fails this *preference*, but does not reject an otherwise eligible issue. | preferred |
| attempt-history | In eval mode, `linked PRs:` under Repo facts plus any additional PRs named in Comments; in live mode, the issue's Development box and PR links in its thread. | Fewer than **two distinct PRs** attempting this issue have been closed without merging. Count the same PR only once even if it appears in both sources. One old abandoned PR alone does not fail this preference. | preferred |

## Verdict rule

**Accept** an issue if and only if **every required check passes**. **Reject** it if **any required check fails or is unclear**; `unclear` means that the specified evidence is genuinely absent after checking the listed sources, not merely that the grader has not looked. A preferred check may be `pass`, `fail`, or `unclear` without changing the accept/reject verdict; use preferred results only to compare accepted issues. Measure all age and recency thresholds against the eval bundle's stated **capture date** in eval mode and against **today** in live mode. In live mode, apply the Path Review claim-comment exception from `scope.md` and use the fit profile only to rank already-accepted issues, never to change a verdict.
